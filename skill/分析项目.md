## 结论：USB忙超时是 MCU 端的"历史粘性错误码"，不是当前实时故障

### 一、关键代码定位

错误码 `3 = USB忙超时` 的产生位置在 [App_usb.c:25-32](file:///d:/sike_local/AiKeyBoard/App/src/App_usb.c#L25-L32)：

```c
#define HID_BUSY_TIMEOUT_TICKS 20   // 0x81 IN 端点忙20个tick判超时

if (hid_state == HID_STATE_BUSY) {
    if (++busy_ticks < HID_BUSY_TIMEOUT_TICKS) return;
    App_debug_set_error(DEBUG_ERROR_USB_BUSY);   // 设置 error_code = 3
    (void)usbd_ep_flush(HID_INT_EP);
    hid_state = HID_STATE_IDLE;                   // ← 关键：自动恢复
    busy_ticks = 0;
    memset(last_report, 0xFF, sizeof(last_report));
    report_dirty = true;
}
```

而 `App_debug_set_error` 在 [App_debug.c](file:///d:/sike_local/AiKeyBoard/App/src/App_debug.c) 里**只写不清**：

```c
void App_debug_set_error(uint8_t error) {
    g_debug.error_code = error;   // 粘住，不会自动归零
}
```

清除的唯一途径是上位机主动发 `DEBUG_PARAM_CLEAR (0x01)` 命令（调用 `App_debug_init()` 清零全部计数）。

### 三、为什么"显示超时却还能打字"

这里存在两条**完全独立**的 USB 数据通路，是理解问题的关键：

| 通路 | 端点/接口 | 用途 | 是否受影响 |
|------|----------|------|-----------|
| 标准 HID Keyboard | IN EP 0x81 | 给操作系统打字 | 正常工作 |
| Custom HID | 独立接口 | 上位机读调试统计/ADC | 上位机只读 error_code 字段 |

1. **error_code 是"最后一次错误"的粘性记录**，不是实时状态。一旦在某时刻被设为 3，就会一直被上位机轮询读到，直到发清除命令。
2. **触发时刻**：16:11→16:47 之间上位机调试通道断开了约 36 分钟。这期间上位机没在轮询，但**标准键盘 EP 0x81 也可能因 PC 端 Suspend/挂起没人取报告**而触发 busy timeout，于是 error_code 被钉成 3。
3. **触发后固件已自愈**：代码里 flush 端点 + `hid_state=IDLE` + `report_dirty=true`，下一轮 `Task_exec` 立即重新提交报告，所以打字功能没受影响。
4. **上位机误判**：[debug_backend.py:576](file:///d:/sike_local/AiKeyBoard/AiKey-Hub/debug_backend.py#L576) 把 error_code==3 直接翻译成"USB忙超时 | 异常：MCU已记录错误"，但没有区分"当前正在发生"和"历史遗留未清除"。

### 四、根因总结

> **上位机显示的 USB忙超时，是 16:11–16:47 调试通道断连期间触发并被固件"粘住"的历史错误码；键盘的标准 HID 通路在那之后已自动恢复，所以照常打字。**

### 五、建议修复方向（任选其一）

1. **固件侧**：在 `App_usb_process_task` 成功发送一帧后，若当前 `error_code == DEBUG_ERROR_USB_BUSY` 则清零（让错误码反映"当前状态"而非"最后一次"）。
2. **上位机侧**：在 [debug_backend.py](file:///d:/sike_local/AiKeyBoard/AiKey-Hub/debug_backend.py) 里把"USB忙超时"判定为"异常"前，先比对 `usb_count` 是否仍在增长 + `state_flags` 的 HID_BUSY 位是否真实置位；或者重连后自动发一次 `DEBUG_PARAM_CLEAR`。

## DMA 死锁根因排查完成

### 一、死锁现场精确定位

从 [keyboard_debug_20260615_085011.log:25218-25220](file:///d:/sike_local/AiKeyBoard/AiKey-Hub/logs/keyboard_debug_20260615_085011.log#L25218-L25220)：

```
13:37:09.408  row=0  dma=86072270  frame=17214454   ← 正常扫描中（row还在0）
13:37:10.015  row=4  dma=86072534  frame=17214506   ← 跳到row=4，dma只+264（应为+5）
13:37:10.463  row=4  dma=86072534  frame=17214506   ← 完全冻结！ADC/DMA未推进
```

**关键证据**：
- `dma` 从 86072270 到 86072534 只增加了 **264**（正常一帧应 +5）
- `row` 卡在 **4** 不再变化
- `main_count` 仍在增长 → 主循环没死，是 DMA 子系统死了

### 二、根因：DMA 中断被 USB 中断饿死/丢失

**中断优先级配置（致命问题）**：

| 中断 | 优先级 | 位置 |
|------|--------|------|
| USB (USBD_IRQn) | **0**（最高，未设置） | [main.c:59](file:///d:/sike_local/AiKeyBoard/User/Src/main.c#L59) 只 `NVIC_EnableIRQ` 未 `SetPriority` |
| DMA1_Channel1 | 1 | [bsp_adc_dma.c:79](file:///d:/sike_local/AiKeyBoard/Bsp/src/bsp_adc_dma.c#L79) |
| DMA1_Channel2 (SPI) | 2 | [bsp_spi_dma.c:44](file:///d:/sike_local/AiKeyBoard/Bsp/src/bsp_spi_dma.c#L44) |
| TASK_TIM | 3 | [bsp_tim.c:18](file:///d:/sike_local/AiKeyBoard/Bsp/src/bsp_tim.c#L18) |

**USB 优先级最高（0）意味着**：当 USB 总线异常（Suspend/Reset/Resume 风暴）时，USB ISR 可以**无限抢占** DMA 中断。

### 三、死锁机制（结合代码）

1. **触发条件**：13:29 左右 PC 端发生 USB 异常（可能是休眠/唤醒/线缆接触），USB ISR 频繁触发
2. **DMA 中断饥饿**：USB ISR（优先级0）持续抢占 DMA ISR（优先级1），导致 [lib_hall_sensor.c DMA1_Channel1_IRQHandler](file:///d:/sike_local/AiKeyBoard/Lib/src/lib_hall_sensor.c#L131-L148) 中的 `g_adc_complete = 1` 迟迟无法执行
3. **超时恢复失效**：[lib_hall_sensor.c:194-206](file:///d:/sike_local/AiKeyBoard/Lib/src/lib_hall_sensor.c#L194-L206) 的看门狗本应恢复：
   ```c
   if ((HAL_GetTick() - g_adc_start_tick) < ADC_SCAN_TIMEOUT_MS) return;
   App_debug_capture_adc_timeout(g_current_row);
   DMA1_Channel1->CCR &= ~DMA_CCR_EN;  // 关DMA
   bsp_adc_dma_start();                 // 重启
   ```
4. **但看门狗也有bug**：`App_debug_capture_adc_timeout` 只在**第一次**超时时记录，且 [App_debug.c](file:///d:/sike_local/AiKeyBoard/App/src/App_debug.c) 里 `error_code` 被钉成 `DEBUG_ERROR_ADC_TIMEOUT` 后，后续每次超时都因 `adc_timeout_count` 未变而**不再触发恢复逻辑的快照**（虽然重启逻辑仍执行）

### 四、为什么第二次日志（141356）没死锁

对比两次固件，第二次加了 [App_debug.c 的 `App_debug_capture_adc_timeout`](file:///d:/sike_local/AiKeyBoard/App/src/App_debug.c) 完整实现，它**每次超时都会强制重启 DMA**：

```c
void lib_hall_sensor_task(void) {
    if (!g_adc_complete) {
        if ((HAL_GetTick() - g_adc_start_tick) < ADC_SCAN_TIMEOUT_MS) return;
        App_debug_capture_adc_timeout(g_current_row);  // ← 新增：强制恢复
        DMA1_Channel1->CCR &= ~DMA_CCR_EN;
        bsp_adc_dma_start();
        return;
    }
```

**但第一次日志（085011）的固件没有这个看门狗恢复**（日志里完全没有 `ADC故障快照`），所以 DMA 一旦卡死就永久死亡。

### 五、修复方案

#### 方案1（推荐）：修复中断优先级 —— 治本

USB 不应是最高优先级。ADC/DMA 是键盘生命线，应优先：

```c
// main.c APP_USBInit() 中
NVIC_SetPriority(USBD_IRQn, 2, 0);   // USB降到优先级2
NVIC_EnableIRQ(USBD_IRQn);

// bsp_adc_dma.c 保持
HAL_NVIC_SetPriority(DMA1_Channel1_IRQn, 1, 0);  // DMA保持1，高于USB
```

#### 方案2：看门狗强制恢复 —— 治标（已部分实现）

确保 [lib_hall_sensor.c:194-206](file:///d:/sike_local/AiKeyBoard/Lib/src/lib_hall_sensor.c#L194-L206) 的超时恢复**每次都执行**，不依赖快照去重：

```c
if (!g_adc_complete) {
    if ((HAL_GetTick() - g_adc_start_tick) < ADC_SCAN_TIMEOUT_MS) return;
    // 强制恢复，无论是否首次
    DMA1_Channel1->CCR &= ~DMA_CCR_EN;
    DMA1->IFCR = ADC_DMA1_CH1_ALL_FLAGS;
    ADC1->CR2 &= ~ADC_CR2_SWSTART;  // 停止ADC
    ADC1->SR = ~(ADC_SR_EOC | ADC_SR_STRT);
    select_row(g_current_row);
    g_adc_start_tick = HAL_GetTick();
    bsp_adc_dma_start();
    return;
}
```

## 为什么 USB 中断优先级会高于 ADC？—— 深度分析

### 一、这不是"有意设计"，而是"遗漏导致的默认值"

### 二、PY32F403 的默认优先级机制

ARM Cortex-M4 的 NVIC 有一个关键特性：

> **复位后，所有中断的优先级寄存器默认值为 0，而 0 是最高优先级（数值越小越高）。**

所以：

```
DMA1_Channel1_IRQn  → 显式设置为 1  ([bsp_adc_dma.c:79](file:///d:/sike_local/AiKeyBoard/Bsp/src/bsp_adc_dma.c#L79))
DMA1_Channel2_IRQn  → 显式设置为 2  ([bsp_spi_dma.c:44](file:///d:/sike_local/AiKeyBoard/Bsp/src/bsp_spi_dma.c#L44))
TASK_TIM_IRQ        → 显式设置为 3  ([bsp_tim.c:18](file:///d:/sike_local/AiKeyBoard/Bsp/src/bsp_tim.c#L18))
USBD_IRQn           → 未设置，默认 0 ← 意外成为最高！
```

**这完全是个 bug，不是设计**。开发者给所有外设中断都写了 `SetPriority`，唯独漏了 USB。

### 三、为什么这种"USB最高优先级"在嵌入式 HID 设备里是常见陷阱

很多 USB HID 键盘固件会犯这个错，原因有三：

#### 1. CherryUSB 等框架的"甩锅"设计

CherryUSB 把中断优先级配置留给用户的 `usb_dc_low_level_init()`（弱定义），但用户往往不知道要重写它。本项目的 [usb_dc_py32.c:162](file:///d:/sike_local/AiKeyBoard/CherryUSB/port/usb_dc_py32.c#L162) 这个函数是空的。

#### 2. USB 协议的"实时性焦虑"误导

USB 协议有严格时序要求（如 SETUP 包必须在 50ms 内响应），很多工程师误以为"USB必须最高优先级才不会丢包"。**但这是错的**：

- USB 全速（Full Speed）每帧 1ms，SETUP 响应窗口 50ms
- DMA 中断延迟几微秒根本不会让 USB 丢包
- 反过来，USB ISR 执行时间（处理枚举/重置/Suspend）可能达**几十到几百微秒**，远超 ADC 采样周期

#### 3. "USB能打字就行"的测试盲区

开发时用"能不能打字"验证，键盘在正常 USB 环境下**永远工作正常**（因为 USB ISR 很短，不会饿死 DMA）。只有在以下**异常场景**才暴露：

- PC 进入睡眠/休眠（USB Suspend）
- 唤醒时的 Resume + Reset 风暴
- USB 线缆接触不良导致反复枚举
- USB Hub 过载

这些异常下 USB ISR 会高频触发，持续几十毫秒，**正好饿死 DMA**。这就是为什么你的两次日志都发生在长时间运行后、且伴随"诊断响应超时"（USB 调试通道也受影响）。

### 五、正确的优先级设计原则

对于 HID 键盘这类设备，正确原则是：

```
DMA/ADC (采样生命线)  >  定时器 (任务调度)  >  USB (通信)
```

因为：
1. **ADC/DMA 是输入源**：没有采样就没有按键数据，USB 发什么？
2. **USB 是输出端**：键盘的 USB 报告本来就是周期性（每帧最多1次），延迟几百微秒无感知
3. **USB 异常不应拖垮核心功能**：即使 USB 挂了，采样链路也应继续，以便 USB 恢复后立即恢复打字

### 四、为什么 USB 不能是最高优先级（理论依据）

针对 HID 键盘设备的具体分析：

| 因素 | USB最高(0)是否合理 | 理由 |
|------|-------------------|------|
| SETUP响应窗口 | ❌ 不需要最高 | USB FS的SETUP窗口50ms，DMA中断延迟μs级根本不触发超时 |
| SOF（1ms帧） | ❌ 不需要最高 | 键盘是中断传输，不依赖SOF同步 |
| 枚举/重置 | ❌ 不需要最高 | 枚举过程是ms级，容忍中断延迟 |
| ADC采样周期 | ✅ 必须保护 | ADC单次约66μs，USB ISR若执行200μs就会让DMA错过3次采样 |
| USB异常风暴 | ✅ 必须保护 | Suspend/Resume/Reset风暴时USB ISR持续触发，会饿死DMA |
