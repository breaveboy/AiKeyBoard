当前 main.c:59 的 USB 和 bsp_spi_dma.c:44 的 SPI 都是 2。两者不互相抢占，意味着：同级别是轮询的方式，是吧

**Assistant**

不是轮询。ARM Cortex-M 对**同优先级中断**的处理机制是：**排队等待，不可抢占**。

### 具体机制

1. **不能互相抢占**：如果一个同优先级 ISR 正在执行，另一个同优先级中断触发时，硬件会把它标记为 **pending（挂起等待）**，不会打断当前 ISR。

2. **当前 ISR 执行完毕后才处理**：等当前 ISR 退出后，硬件才会去处理 pending 中的同优先级中断。

3. **多个同优先级同时 pending 时**：按**中断向量号（IRQn 编号）**决定先后顺序，编号小的先执行，**不是轮询，也不是随机**。

### 对当前项目的影响

USB(2) 和 SPI(2) 同优先级时：

```
场景：USB ISR 正在执行，此时 SPI DMA 完成
       ↓
SPI 中断进入 pending 状态（挂起）
       ↓
USB ISR 执行完毕，退出
       ↓
硬件自动跳转到 SPI ISR 执行
```

**延迟** = USB ISR 的执行时间。因为两个 ISR 都很短（μs 级），实际影响可忽略。

### 如果想避免这个等待

把 USB 设为比 SPI 高一级即可让 USB 能抢占 SPI：

```
ADC(1) > USB(2) > SPI(3) > TIM6(4)
```

但对键盘应用来说，当前 `USB(2) = SPI(2)` 的配置已经够用，不需要改。

### 二、真正瓶颈：异步任务调度引入的"跨轮次"延迟

关键在于扫描是**异步**的，每行之间隔着一次 `Task_exec` 循环：

```

  → 立即返回（ADC在后台跑）

Task_exec第N+1轮:  ← 这里可能有延迟！
  → lib_hall_sensor_task: 检测到 g_adc_complete=1
  → ...
```

**主循环 `while(1){Task_exec();}` 的单次迭代耗时**决定了一切。`Task_exec` 每轮要遍历 6 个任务（[task.c:12-19](file:///d:/sike_local/AiKeyBoard/User/Src/task.c#L12-L19)），其中 `period=1` 的任务（`App_adkey_scan_task`、`App_usb_process_task`、`App_protocol_task`）**每个 g_cnt tick 只执行一次**。

### 三、致命瓶颈：TIM6 tick 频率 = 1ms

[bsp_board.h:119-120](file:///d:/sike_local/AiKeyBoard/Bsp/inc/bsp_board.h#L119-L120)：

TIM6 中断频率 = 144MHz / 1000 / 144 = **1000Hz = 每1ms一次**

`Task_update()` 每 **1ms** 才 `g_cnt++` 一次。

这意味着 `period=1` 的任务（包括 USB 上报 `App_usb_process_task`）**最快每 1ms 才执行一次**。

### 四、完整一帧的时序（实测约1ms的原因）

```
t=0      lib_hall_sensor_task: row0 ADC启动（后台23μs完成）
t=25μs   DMA中断: g_adc_complete=1
         下一次Task_exec（几乎立即）: 处理row0，启动row1

         App_usb_process_task 执行（USB上报）

```

**结论：USB 上报被 TIM6 的 1ms 节拍锁死在最快 1KHz。但由于一帧扫描（200μs）+ 按键处理 + 等待下一个 tick，实际回报率被限制在 1ms/tick ≈ 1000Hz 上限，且由于 tick 对齐延迟，有效回报率通常低于此值。**

### 五、你测到 PMOS 输出 1ms 周期的原因

PMOS 波形反映了 `select_row()` 的行切换。5行连续扫描约200μs后，`g_scan_complete=1`，然后 `ROW_ALL_OFF()` 关闭所有行（[lib_hall_sensor.c:415](file:///d:/sike_local/AiKeyBoard/Lib/src/lib_hall_sensor.c#L415)）。之后要等到下一个 1ms tick 才通过 `release_frame` 重启扫描。

所以 PMOS 上看到：**200μs 活跃 + 800μs 空闲 = 1ms 周期**。

### 二、根因：`App_usb_process_task` 的 `period=0` 导致 USB 端点被疯狂重写

当前配置（你测试的版本）：
```c
{0, 0,  lib_hall_sensor_task},     // period=0
{0, 0,  App_adkey_scan_task},      // period=0（你没改回1）
{0, 0,  App_usb_process_task},     // period=0
```

**致命问题**：`App_usb_process_task` 是 `period=0`，意味着**每次 `Task_exec` 循环都调用它**。主循环 144MHz 跑得极快，循环间隔约 **1-2μs**。

看 [App_usb.c:24-121](file:///d:/sike_local/AiKeyBoard/App/src/App_usb.c#L24-L121) 的逻辑：

```c
void App_usb_process_task(void) {
    if (hid_state == HID_STATE_BUSY) {
        if (++busy_ticks < HID_BUSY_TIMEOUT_TICKS) return;  // 等20次
        // 超时处理...
    }
    if (!report_dirty) return;
    // ... 构建 report ...
    int ret = usbd_ep_start_write(HID_INT_EP, ...);  // 发送
}
```

**USB 全速端点（Full Speed）的最小传输间隔是 1ms（一个 frame）**。但 `period=0` 的任务每 ~2μs 就检查一次 `hid_state`，一旦 BUSY 解除就立即提交下一帧。

这导致了一个竞态风暴：
1. `usbd_ep_start_write` 提交报告，`hid_state = HID_STATE_BUSY`
2. USB 硬件还没完成传输（需要等下一个 1ms SOF）
3. `period=0` 的任务在 2μs 后再次执行，发现 `hid_state == BUSY`，`busy_ticks` 从 0 开始计数
4. **但 `busy_ticks` 是 static，每次 `Task_exec` 都 +1**，20 次循环只需 ~40μs 就触发超时
5. 超时后 `usbd_ep_flush` + 强制 IDLE + `report_dirty = true`
6. 立即再次 `usbd_ep_start_write` → 又 BUSY → 又 40μs 超时 → **无限循环**

### 三、为什么 `HID_BUSY_TIMEOUT_TICKS = 20` 在 `period=0` 下是灾难

```c
#define HID_BUSY_TIMEOUT_TICKS 20
```

这个值原本设计给 `period=1`（1ms 节拍），即等 20ms 才判超时。

但 `period=0` 时，`busy_ticks` 每次主循环 +1，20 次只需 **~40μs**。USB 端点根本不可能在 40μs 内完成传输（USB FS 一个 frame = 1ms），所以**每次都会触发超时**，疯狂 flush + 重写端点，最终把 USB 协议栈搞崩。

## USB HID 键盘回报率的影响因素

回报率（Polling Rate）= 操作系统每秒从键盘读取报告的次数，从源头到终点共 4 层瓶颈：

### 1. USB 协议物理层（硬上限：1KHz）

这是**不可突破的天花板**。

- USB 全速（Full Speed, 12Mbps）使用 **1ms SOF（Start of Frame）** 帧结构
- 主机每个 frame（1ms）做一次 IN 轮询，设备只能在被轮询时提交数据
- 所以理论最高 = **1000 次/秒 = 1KHz**
- 唯一突破方法：换 USB 高速（High Speed, 480Mbps），微帧 125μs，可达 8KHz。但 PY32F403 只支持 USB FS，**硬件无法突破**

### 2. 主机端轮询间隔（由 HID 描述符决定）

固件的 HID 描述符中有一个 `bInterval` 字段，告诉主机多久轮询一次：

- 当前项目 `bInterval` 值决定主机轮询周期
- Full Speed 下 `bInterval=1` = 每 1 个 frame 轮询 = **1KHz**
- 如果 `bInterval=2` = 每 2 个 frame = 500Hz（被腰斩）

这是**固件可控**的，必须确保 `bInterval=1`。

### 3. 固件上报时机（我们刚优化的）

即使主机每 1ms 轮询一次，固件也必须**提前准备好数据**：

```

  t=0ms     按键按下 → ADC扫描完成
  t=0.5ms   帧完成，但要等下一个tick
  t=1ms     tick到，处理按键，提交USB报告 → 但本轮SOF已过
  t=2ms     下一个SOF，主机取走 → 延迟2ms

改后（500μs tick）：
  t=0ms     按键按下 → ADC扫描完成
  t=0.25ms  帧完成，等下一个tick
  t=0.5ms   tick到，处理按键，提交USB报告
  t=1ms     下一个SOF，主机取走 → 延迟1ms
```

这就是改 500μs tick 的收益：**把"准备数据"的延迟减半**。

## USB 是"主从架构"

### 一句话回答

USB 协议规定：**所有通信都由主机发起**。设备不能主动说话，只能被问到才能回答。

### 为什么这么设计

USB 总线是**共享的**（一根线缆接多个设备）。如果设备能主动发送，多个设备同时说话就会冲突。所以协议规定：

```
主机（PC）                          设备（键盘）
   │                                    │
   │──── "轮到你1号了，有数据吗？" ────→│   IN令牌包
   │                                    │
   │←──────── "有，这是按键数据" ────────│   DATA包
   │                                    │
   │─────── "收到了" ─────────────────→│   ACK包
   │                                    │
   │         （等待下一个frame）          │
   │                                    │
   │──── "轮到你1号了，有数据吗？" ────→│   下一个frame
   │                                    │
```

设备**永远不能先开口**，只能等主机问。

### Full Speed 的 1ms frame

主机用 SOF（Start of Frame）包标记每个 frame 的开始，每 **1ms** 一个。在每个 frame 内，主机按调度表依次轮询各个端点：

```
Frame 0 (0~1ms):  ──SOF── [轮询键盘] [轮询鼠标] [轮询U盘] ──
Frame 1 (1~2ms):  ──SOF── [轮询键盘] [轮询鼠标] [轮询U盘] ──
Frame 2 (2~3ms):  ──SOF── [轮询键盘] [轮询鼠标] [轮询U盘] ──
```

主机决定**什么时候问、问谁、多频繁问**，全由端点描述符的 `bInterval` 告诉主机：

```
bInterval=1 → 每个 frame 都问 → 1ms 一次 → 1000Hz
bInterval=5 → 每 5 个 frame 问一次 → 5ms 一次 → 200Hz（或16ms，取决于实现）
```

### 对比其他协议

| 协议 | 谁主动 | 设备能随时发吗 |
|------|--------|--------------|
| **USB** | 主机 | ❌ 不能，必须等轮询 |
| 蓝牙 | 主从均可 | ✅ 可主动通知 |
| PS/2 | 设备 | ✅ 设备主动中断通知 |
| UART | 均可 | ✅ 随时发 |

PS/2 键盘为什么理论延迟更低？因为它是中断驱动——按键按下瞬间，键盘立刻主动向 CPU 发中断信号。而 USB 键盘必须把数据准备好，等 PC 来问。

### 所以回报率的天花板

```
主机每 1ms 问一次（bInterval=1）
  → 设备最多每 1ms 回答一次
    → 最高 1000 次/秒 = 1KHz

固件把数据准备得再快也没用——如果主机还没问，数据只能等在端点缓冲区里。
```

唯一突破 1KHz 的方法：用 USB High Speed（480Mbps），它的 frame 变成 **125μs 微帧**（bInterval=1 → 8000Hz）。但 PY32F403 只支持 Full Speed，硬件决定了上限就是 1KHz。

## `App_ota_flush_page` 函数分析

这是 OTA 升级中的 **Flash 页写入函数**，把缓存在 RAM 中的固件数据刷写到 Flash。

### 逐行解释

```c
static OtaStatus_t App_ota_flush_page(void) 
{
    uint32_t page_offset;

    // 1. 如果缓冲区没数据，直接返回（没什么可写的）
    if (g_ota.page_length == 0U) { 
        return OTA_STATUS_OK; 
    }

    // 2. 计算这批数据在Flash中的写入偏移
    //    received_size = 已接收的总字节数
    //    page_length = 当前缓冲区里还没写入的字节数
    //    差值 = 这批数据的起始位置
    page_offset = g_ota.received_size - g_ota.page_length;

    // 3. 写入Flash（下载区，偏移量，数据，长度）
    if (bsp_flash_write(BSP_FLASH_REGION_DOWNLOAD, page_offset,
                        g_ota.page_buffer, g_ota.page_length) != BSP_FLASH_OK) {
        g_ota.state = OTA_STATE_ERROR;
        return OTA_STATUS_FLASH_ERROR;
    }

    // 4. 清空缓冲区，准备接收下一批数据
    memset(g_ota.page_buffer, 0xFF, sizeof(g_ota.page_buffer));
    g_ota.page_length = 0U;
    return OTA_STATUS_OK;
}
```

### 为什么需要这个函数

OTA 数据是通过 USB HID 包（每包最大 63 字节）分批发送的，但 Flash 写入要求**按页（Page）对齐**。所以需要一个 RAM 缓冲区做"蓄水池"：

```
USB包1(63B) → page_buffer[0~62]      page_length=63
USB包2(63B) → page_buffer[63~125]    page_length=126
USB包3(63B) → page_buffer[126~188]   page_length=189
...
page_buffer满了(BSP_FLASH_PAGE_SIZE) → flush_page() 写入Flash
```

### 调用时机

两个地方调用 `flush_page`：

**1. 缓冲区满时**（[App_ota.c:301-302](file:///d:/sike_local/AiKeyBoard/App/src/App_ota.c#L301-L302)）：
```c
if (g_ota.page_length == BSP_FLASH_PAGE_SIZE) {
    App_ota_flush_page();  // 攒满一页，写入Flash
}
```

**2. 传输完成时**（[App_ota.c:331](file:///d:/sike_local/AiKeyBoard/App/src/App_ota.c#L331)）：
```c
// App_ota_end() 中
status = App_ota_flush_page();  // 写入最后不足一页的剩余数据
```

### `page_offset` 计算的意义

```c
page_offset = g_ota.received_size - g_ota.page_length;
```

举例：已接收 1000 字节，缓冲区里还有 200 字节没写入 Flash，说明前 800 字节已经写过了，这 200 字节应该写到 Flash 的偏移 800 处。

```
Flash: [0~~~800已写入][800~~~1000待写入]
                        ↑ page_offset = 1000-200 = 800
```

不是。`received_size` 不是数据包的大小，是**MCU 这边自己记录的"我已经收到了多少字节"的计数器**。

### 两个值的来源完全不同

```
packet_offset      → 上位机发出的，告诉MCU"这包从第N字节开始"
g_ota.received_size → MCU自己算的，"我到现在为止已经收了N字节"
```

### 为什么要比较它们

USB 传输可能**丢包或乱序**。比如上位机发了5包：

```
正常顺序：
  包1: offset=0    → MCU收到，received_size=0  → 匹配✓ → 收63字节 → received_size=63
  包2: offset=63   → MCU收到，received_size=63 → 匹配✓ → 收63字节 → received_size=126
  包3: offset=126  → MCU收到，received_size=126→ 匹配✓ → 收63字节 → received_size=189

如果包3丢了，包4先到：
  包4: offset=189  → MCU收到，received_size=126 → 不匹配！✗
                     说明中间有包丢了，拒绝这包
```

### 为什么不能直接信任 packet_offset

如果直接用上位机给的 `packet_offset` 写入 Flash，万一中间丢了一包：

```
包1 offset=0    → 直接写Flash[0]
包2 offset=63   → 直接写Flash[63]
包4 offset=189  → 直接写Flash[189]  ← 中间126~188是空的（0xFF）
                                         ↑ 固件数据有空洞，升级后变砖
```

所以 MCU 必须自己用 `received_size` 来确认：**你说的位置 = 我期待的位置**，才能保证数据连续无空洞。

### 一句话总结

```
packet_offset  = 上位机说"这是第N字节"
received_size  = MCU说"我只收到了N字节"
两者相等 = 数据连续，没丢包，可以继续接收
两者不等 = 中间丢包了，拒绝这包，等待重传
```

### 第⑦步：重启 — `App_ota_request_reboot` + `App_ota_task`

```c
static OtaStatus_t App_ota_request_reboot(void) {
    if (g_ota.state != OTA_STATE_READY) {
        return OTA_STATUS_INVALID_STATE;
    }
    g_ota.reboot_pending = true;                    // 标记"准备重启"

}

void App_ota_task(void) {
    if (!g_ota.reboot_pending) return;

    // 等200ms（让USB把回复发给上位机后再重启）
    if ((HAL_GetTick() - g_ota.reboot_request_tick) < APP_OTA_REBOOT_DELAY_MS) {
        return;
    }

    g_ota.reboot_pending = false;
    __disable_irq();           // 关中断
    NVIC_SystemReset();        // 芯片复位，重启进入Bootloader
}
```

### Flash 内存布局

```
Flash物理地址：
┌─────────────────────────┐ 0x08000000
│ Bootloader (16KB)        │  开机先跑这里，检查info区
│                          │  如果有新固件 → 搬到APP区 → 跳转
├─────────────────────────┤
│ Info区 (1扇区)           │  存固件元信息：大小/CRC/版本
├─────────────────────────┤
│ Download区 (下载区)      │  ← OTA数据写到这里
│ 固件数据临时存放在这里     │
├─────────────────────────┤
│ APP区 (应用程序)          │  ← 当前运行的程序
│ 你现在的代码在这里        │
└─────────────────────────┘
```

重启后 Bootloader 读 Info 区，发现标记 READY，就把 Download 区的固件搬到 APP 区，完成升级。
